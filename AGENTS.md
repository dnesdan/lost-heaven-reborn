# Development conventions

- Keep code and documentation in English; communicate with the user in Czech.
- This is a Rust workspace. Keep the engine, gameplay and rendering in Rust; use wgpu, Vulkan on Linux and Metal on macOS. Avoid adding large frameworks or runtime dependencies without a concrete need.
- Target the user's original, legally obtained PC installation as game data. Do not require the original executable or REA at runtime. Keep game files, extracted/converted assets, binaries, private URLs, credentials, analysis databases and decompiler output outside Git. Use synthetic public fixtures.
- REA is the mandatory primary reverse-engineering tool, with Ghidra where supported. Record binary hashes, function addresses, evidence and confidence privately. Separate file-format findings, static analysis, implementation and original-runtime validation. Do not infer runtime behavior from decompiler output alone.
- Keep README, coverage and progress documentation concise and evidence-based. State the current Rust rewrite status independently of useful historical analysis or prototype evidence.
- Reconstruct functions in dependency order using contracts keyed by original binary SHA-256 and canonical entry RVA. Record callers, state changes, numeric behavior, ownership, native evidence, Rust symbols and validation; unresolved function boundaries receive no function credit.
- Prefer evidenced original function and type names, adapting function names to Rust snake_case where appropriate. Distinguish original symbols from names assigned by upstream researchers. When the original name is unknown, use an explicitly descriptive working name and retain the binary/RVA mapping; never present a guessed name as original. Use evidenced original library boundaries for new namespaces; upstream folder organization is inspiration, not proof of original packages.
- Express semantic engine and gameplay operations through logically named typed live views or actual resource owners. Replace anonymous CPU maps and offset/pointer plumbing at these call sites with named accessors and ordered operations; keep raw layout access in narrow storage/backend adapters and explicit binary-boundary or diagnostic code. Derive names from evidenced PC/PS2 symbols where available, without inventing original members or mirrored object layouts.
- Views must borrow the actual state and read it when the original operation does. Preserve aliases, pointer redirection, lazy reads, callback mutations, effect order, exact numeric/bit behavior and reached error prefixes. Do not replace live access with decoded snapshots, eager validation, cached values across mutating callbacks or invented defaults. Descriptive helper phases do not receive original-function credit.
- Derive scalar width, signedness, alignment and conversion or truncation behavior from evidenced PC/PS2 instructions and the applicable ABI for each contract. Do not infer them from an upstream type alias, decompiler spelling or host type; for example, `ulong` does not by itself establish `u64`.
- Generate README progress locally from the versioned public metadata snapshot. Keep static analysis, implemented behavior and original-runtime comparisons separate; unknown coverage is N/A. Preserve historical snapshots and keep the canonical research ledger private. Do not add CI.
- Use pinned dependencies and `Cargo.lock`. Run `scripts/test.sh` for workspace changes. Report build, logic, rendered and interactive verification separately; do not claim features that were not exercised.
- Work on the designated task branch (currently `rust-engine`) by default in the current checkout. Do not create additional worktrees or CI workflows unless requested.
- The immediate gameplay goal is a playable first mission from the original menu through its original objectives and completion. Reconstruct dependencies in order; isolated helpers or static inspection do not satisfy this gate. Track LS3DF/library parity with the pinned mafia-re reference separately from Game.exe mission compatibility; see `docs/GOALS.md`.
- Prioritize general engine functions and their interactions across original content. Specific models, animations and missions are regression inputs, not implementation special cases or substitutes for engine-wide support.
- Use actual PS2 linker/debug symbol evidence to recover original names and cross-check PC behavior. Record the symbol's binary hash/address and the evidence for its PC correspondence. Linker names alone do not establish class member layouts or equivalent platform semantics.
- The orchestrator assigns each implementation milestone to one owner. Use only Sol agents for delegated reconstruction, implementation, probes and reviews; prefer Sol 6.1 (`gpt-6.1-sol`) when selecting a model, and use independent work to fill available slots. Every substantial code milestone receives two sequential independent reviews; authors do not review their own work, findings are fixed between rounds, and reviewers verify the final revised diff.
- Research enhanced assets as an optional future mode. Preserve original-data compatibility and fidelity first; proposed texture/model upgrades must retain gameplay-relevant structure and remain outside the canonical behavior implementation.
- Preserve history and user work; never force-push. Audit staged files and outgoing commits for private data.
- Record the base commit and source hashes before editing private adaptations. Keep reviewed revisions immutable. Rebase against new source with a three-way comparison, preserving current owners, guards and tests; never replace a newer tree with complete files from an older copy.
- Track task-owned processes and temporary state. Stop only verified task-owned processes gracefully, then use bounded termination if needed. Preserve user files, inputs, saves, caches, tools and useful evidence; remove only owned scratch files.
